# Инструкции Codex по работе с кодом проекта

## Язык и стиль общения

- С пользователем отвечать на русском.
- Имена файлов, классов, функций, переменных и ключей оставлять на английском.
- В коде сохранять текущий стиль проекта: async/await, сервисные классы, SQLAlchemy 2.0 typed mappings, aiogram Router/FSM.
- В проекте много русских комментариев и текстов. Сохранять файлы в UTF-8. Не править текст только из-за mojibake в выводе PowerShell.

## Общие правила правок

- Не переписывать крупные handler-файлы без необходимости. Делать точечные изменения рядом с существующей логикой.
- Не менять пользовательские незакоммиченные изменения без явной просьбы.
- Не коммитить `.env`, токены, mnemonic, cookies Fragment, реальные wallet/session данные.
- Для новых настроек использовать `settings`/`BotSettingsService`, если настройка должна меняться из админки.
- Для обязательных переменных окружения добавлять проверку в `src/config.py` и пример в `.env.example`.
- Для новых таблиц или колонок всегда добавлять Alembic-миграцию в `src/db/migrations/versions/`.
- Не использовать `float` для денег, цен, балансов, курсов и TON/USDT сумм. Использовать `Decimal` и явные строки вроде `Decimal("0.000000")`.

## Слои ответственности

- `handlers` отвечают за Telegram UI, FSM, ввод пользователя и вызовы сервисов.
- `keyboards` отвечают только за клавиатуры и callback data.
- `services` отвечают за бизнес-логику, транзакции, балансы, заказы, платежи и настройки.
- `models` описывают структуру данных и индексы, но не содержат бизнес-логику.
- `core/queue.py` отвечает за очередь, retry metadata и Redis/in-memory совместимость.
- `workers` отвечают за фоновое выполнение заказов, retry, recovery и callbacks уведомлений.
- `api_clients` отвечают за внешние API. Не смешивать там Telegram UI, SQLAlchemy-сессии и бизнес-правила.

## Финансы, заказы и балансы

- Любое списание или начисление баланса должно быть атомарным и отражаться в `Transaction` и `BalanceLedger`, если это пользовательский баланс.
- При списании баланса блокировать пользователя через `select(...).with_for_update()`.
- Перед выполнением заказа проверять статус. Не выполнять Fragment-операцию для уже завершенного/отмененного заказа.
- Для повторов использовать существующие статусы и методы `OrderService`: `set_processing`, `set_completed`, `set_failed`, `return_to_pending`, `retry_order`.
- Не добавлять новые строковые статусы без обновления enum-ов, проверок, админки и миграций при необходимости.
- Учитывать разные продукты: `stars` и `premium`. Не писать логику, которая молча работает только со Stars, если сценарий общий.

## Очередь и воркеры

- Очередь должна работать через интерфейс `OrderQueue`, чтобы `InMemoryQueue` и `RedisQueue` оставались совместимыми.
- Redis-реализация должна ack-ать обработанные заказы через `ack`, чтобы не оставлять мусор в `orders:processing`.
- Delayed retry не должен блокировать caller.
- Supervisor должен оставаться устойчивым к падению воркера и изменению числа активных Fragment-аккаунтов.
- Не выполнять реальные Fragment/TON платежи в тестах по умолчанию.

## Telegram UI и локализация

- Для пользовательских текстов проверять `src/locales/ru.yml` и `src/locales/en.yml`.
- Если добавлен новый пользовательский текст, добавить ключи минимум для `ru` и `en`.
- Callback data делать короткими и совместимыми с лимитами Telegram.
- При редактировании сообщений использовать существующие helper-ы `safe_edit_message`, `edit_bot_message`, `safe_delete_message`, если они уже есть в модуле.
- Не ломать FSM-навигацию назад/отмена. Для каждого нового шага должен быть понятный выход.

## База данных

- Использовать `AsyncSession`.
- Коммиты делать на границах сценариев, как уже принято в окружающем коде. Не коммитить внутри низкоуровневого helper-а без причины.
- Для массовых обновлений проверять `rowcount` и статусные условия.
- Добавлять индексы для новых частых фильтров в админке, очереди или истории пользователя.
- Не хранить структурированные данные как строку, если уже есть явный столбец. Если проект уже хранит конкретное поле JSON-строкой, сохранять совместимость.

## Внешние API и безопасность

- Любые вызовы CryptoBot, TON, Fragment должны иметь обработку сетевых ошибок и понятную классификацию retryable/permanent, если это влияет на заказ.
- Не логировать секреты: токены, mnemonic, session cookies, invoices с чувствительными metadata.
- Для Fragment-аккаунтов использовать `FragmentAccountService` и шифрование mnemonic.
- При изменении платежной логики отдельно проверить идемпотентность webhooks/check-payment flows.

## Тестирование

- Для очереди запускать `pytest tests/test_fragment_load.py -v -s -k "queue"`.
- Для supervisor запускать `python -m tests.test_worker_supervisor` в mock-режиме.
- Dry-run с реальным Fragment API запускать только если это явно нужно.
- Для изменений в обработчиках минимум проверять импорты измененных модулей и синтаксис.
- Для изменений БД проверять, что Alembic видит новую миграцию и модели импортируются.

## Типичные риски проекта

- Двойное списание или двойное начисление при повторном callback, retry или падении воркера.
- Потеря заказа между `processing` и `ack`.
- Несогласованность `users.balance_*`, `transactions` и `balance_ledger`.
- Сломанные callback data после изменения клавиатур.
- Отсутствующая локализация на одном из языков.
- Случайный реальный платеж в тесте или dry-run.
- Утечка Fragment/TON/CryptoBot секретов в логи, документы или git.
