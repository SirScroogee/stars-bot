# Архитектурные решения

## ADR-001: Выбор ORM и паттерна доступа к данным

**Статус:** Принято

**Контекст:** Нужен асинхронный доступ к PostgreSQL с поддержкой миграций.

**Решение:** SQLAlchemy 2.0 async + Alembic

**Обоснование:**
- Нативная поддержка async/await
- Декларативные модели с type hints
- Alembic для версионирования схемы
- asyncpg как драйвер (высокая производительность)

## ADR-002: Структура баланса пользователя

**Статус:** Принято

**Контекст:** Нужна полная история изменений баланса с возможностью аудита.

**Решение:** Двойная система: `users.balance_*` + `balance_ledger`

**Обоснование:**
- `users.balance_stars/balance_usdt` — текущий баланс (быстрый доступ)
- `balance_ledger` — журнал всех операций (аудит, сверка)
- Атомарное обновление: UPDATE users + INSERT balance_ledger в одной транзакции

## ADR-003: Идемпотентность заказов

**Статус:** Принято

**Контекст:** Защита от дублирования заказов при повторных запросах.

**Решение:** Уникальный `order_key` генерируется клиентом

**Формат:** `{user_id}:{product}:{timestamp}:{nonce}`

**Обоснование:**
- UNIQUE constraint на `order_key`
- При повторном запросе — возврат существующего заказа
- Защита от double-spending

## ADR-004: Хранение Enum в БД

**Статус:** Принято

**Контекст:** Нужно хранить статусы и типы в читаемом виде.

**Решение:** VARCHAR с проверкой на уровне приложения (Python Enum)

**Обоснование:**
- Читаемость в БД без JOIN
- Гибкость при добавлении новых значений (без ALTER TYPE)
- Валидация через SQLAlchemy Enum type

## ADR-005: Реферальная система

**Статус:** Принято

**Контекст:** Многоуровневая реферальная программа (до 3 уровней).

**Решение:**
- `users.referrer_id` — прямой реферер
- `referral_earnings` — история начислений с указанием уровня
- Проценты хранятся в `settings`

**Обоснование:**
- Простая структура без рекурсивных связей
- Быстрый расчёт при покупке (до 3 JOIN)
- Полная история для отчётов

## ADR-006: Архитектура Fragment Client

**Статус:** Принято

**Контекст:** Нужен надёжный клиент для работы с Fragment API с разделением ответственности.

**Решение:** Трёхуровневая архитектура:
1. `FragmentClient` — низкоуровневый HTTP-клиент
2. `PaymentService` — бизнес-логика покупок
3. `OrderWorker` — обработка очереди заказов

**Обоснование:**
- FragmentClient не знает о заказах и БД
- PaymentService маппит ошибки в доменные типы
- OrderWorker обеспечивает идемпотентность и retry
- Lazy-init кошелька (один раз при первом использовании)

## ADR-007: Очередь заказов

**Статус:** Принято

**Контекст:** Нужна надёжная обработка заказов с retry и восстановлением после падений.

**Решение:** Абстракция `OrderQueue` с реализациями:
- `InMemoryQueue` — для разработки
- `RedisQueue` — для продакшена (TODO)

**Жизненный цикл заказа:**
```
PENDING → PROCESSING → SUCCESS
                    ↘ FAILED → (retry?) → PROCESSING
                              ↘ CANCELLED (max retries)
```

**Гарантии:**
- Один заказ = один результат (idempotent)
- Retry с exponential backoff
- Восстановление застрявших заказов при старте

## ADR-008: Доменные исключения Fragment

**Статус:** Принято

**Контекст:** Нужно различать типы ошибок для корректного маппинга в статусы.

**Решение:** Иерархия исключений:
```
FragmentError (базовый)
├── FragmentAPIError
│   ├── SessionExpiredError
│   └── RateLimitError
├── RecipientNotFoundError
├── InsufficientFundsError
└── TransactionError
    └── TransactionTimeoutError
```

**Маппинг в статусы:**
- `RecipientNotFoundError` → FAILED (без retry)
- `SessionExpiredError` → FAILED (требует ручного вмешательства)
- `InsufficientFundsError` → retry (после пополнения)
- `TransactionError` → retry
- `TransactionTimeoutError` → retry
